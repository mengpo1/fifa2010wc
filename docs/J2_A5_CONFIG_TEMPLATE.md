# J2, étape A5 — Gabarit du manifeste de génération de code

> Étape A5 de `docs/J2_PLAN.md` (§3.5), sous l'autorisation PA-0 (D-015). **Phase A :
> aucune donnée du jeu.** Le gabarit et l'outil ne sont essayés que sur des dossiers
> privés synthétiques, sans aucun XEX.
> Étiquettes : **[V]** fait vérifié, **[H]** hypothèse, **[I]** inconnue.

## 1. Résultat

- **Le gabarit** : `config/private-template/wc2010_manifest.toml`. C'est un manifeste de
  `rexglue codegen` pour les deux modules du jeu :
  - il ne contient que des chemins relatifs vers le dossier privé ;
  - il ne contient aucune adresse du jeu (CP-7) ni aucune valeur propre au disque ;
  - il déclare la version du SDK, `0.11.0`.
- **L'outil** : `tools/private_project.py`, empaqueté en `nix run .#private-project`.
  - `template` contrôle le gabarit du dépôt ;
  - `init` le copie dans `$WC2010_PRIVATE_DIR/project/`, après le contrôle CP-1 ;
  - `check` contrôle la copie privée.
- **Le critère de sortie est rempli** [V] :
  - le gabarit se résout sur un dossier privé synthétique, d'après l'outil et d'après
    l'analyseur de ReXGlue lui-même (§5) ;
  - le dépôt ne contient aucun chemin absolu ni aucune valeur propre au disque : le
    contrôle `template` l'impose (§4) ;
  - le contrôle des données passe.
- **Hors du gabarit**, ajouté à la copie privée en phase B seulement : les débuts de
  fonctions, les pointeurs de code, `setjmp` et `longjmp`, les crochets et
  `function_table_base` (`docs/J2_A3_FUNCTION_TABLE.md` §7).

## 2. Ce que la génération de code impose [V]

Lu dans ReXGlue v0.11.0 (`a3e1d82`), en complément de `docs/J2_A1_SDK_INVENTORY.md` §3.1 :

| Règle | Référence | Conséquence pour le gabarit |
|---|---|---|
| Tous les chemins se résolvent par rapport au dossier du manifeste | `src/codegen/manifest.cpp:77`, `src/codegen/project_recompiler.cpp:304` | Le gabarit est copié dans le dossier privé, et la copie n'a besoin que de chemins relatifs |
| Les deux XEX doivent se trouver sous `game_root`, sinon la génération échoue | `src/codegen/project_recompiler.cpp:324-328,386-391` | `file_path` pointe dans `game/`, l'arborescence extraite. Le dossier `xex/` de `ISO_REQUIREMENTS.md` §6 ne sert pas à la génération |
| Le dossier de sortie est purgé des fichiers qui ressemblent à une sortie non produite | `src/codegen/codegen_writer.cpp:131-179,471-488` | Un dossier par binaire, sous `generated/`, sans chevauchement |
| `codegen.d`, `codegen.build.stamp`, `module_registry.cpp` et `dll_targets.cmake` vont dans le dossier de sortie du module d'entrée | `src/codegen/project_recompiler.cpp:596-612,622-623,653,692` | Ils restent sous `generated/default/` |
| Le manifeste est réécrit après chaque génération réussie : `[project].sdk_version` y est inscrit, ligne par ligne | `src/rexglue/command/codegen_command.cpp:199-209`, `src/codegen/manifest.cpp:204-261` | La copie privée change ; le gabarit, jamais. `init` n'écrase jamais une copie existante |
| `sdk_version` n'est qu'informatif : il est affiché (« project last generated by »), pas comparé | `codegen_command.cpp:119-123` | Le gabarit déclare `0.11.0`, la version que la génération y inscrirait (`REXGLUE_VERSION_FLOOR`) |
| `hook_sources` est facultatif | `src/codegen/project_recompiler.cpp:281` | Absent du gabarit : J2 n'a pas de crochet. J3 en ajoutera à la copie privée |
| Un module exige `guest_path` | `src/codegen/manifest.cpp:135-160` | Voir §3 |

## 3. Le module `fifadllzf.xex` et son `guest_path`

Le gabarit déclare
`guest_path = "\\Device\\Harddisk0\\Partition1\\fifadllzf.xex"` : c'est la voie 1 du
correctif 0002, la configuration sans correctif (`docs/J2_A2_SDK_PATCHES.md` §3.1), retenue
d'abord par l'orchestrateur (§5 du même document).
- [V] Ce chemin se normalise en `device/harddisk0/partition1/fifadllzf.xex`, comme le
  chemin que le runtime forme en joignant le nom nu au dossier de `default.xex`. Un test
  le vérifie avec une transcription de `NormalizeGuestPath` (`src/base/path.cpp:254-270`).
- [H] Cela suffit si le jeu charge son module par son seul nom. **C'est une hypothèse, à
  essayer localement après PB-0.** Le correctif 0002 n'est écrit que si elle échoue.

## 4. L'outil `tools/private_project.py`

| Commande | Ce qu'elle fait | Ce qu'elle refuse |
|---|---|---|
| `template` | Contrôle le gabarit du dépôt | Les règles de `check`, et en plus : une autre version du SDK ; toute clé hors de la liste du gabarit (adresses, `function_table_base`, `setjmp_address`, tables `[functions]` et autres) ; un chemin qui ne sort pas de `project/` |
| `init` | Contrôle le dossier privé par `private_guard check-dir` (CP-1), puis le gabarit. Copie le gabarit en `project/wc2010_manifest.toml` (mode `0600`, dossier `0700`) et crée les dossiers de sortie (`0700`). Contrôle enfin la copie | Un dossier privé qui échoue à CP-1 : **rien n'est écrit**. Un gabarit qui échoue à `template` : rien n'est écrit. **Une copie déjà présente n'est jamais écrasée** |
| `check` | Contrôle la copie privée et affiche où chaque chemin se résout | Un chemin absolu, avec `~`, une lettre de lecteur ou des `\` ; un chemin qui se résout hors du dossier privé, liens symboliques suivis ; un XEX hors de `game_root` ; un dossier de sortie hors de `generated/`, égal à `generated/`, partagé ou imbriqué ; un `guest_path` en double ; un nom de projet invalide ; un `game_root` absent ; un TOML invalide |

- `check` accepte les clés ajoutées en phase B, notamment les adresses : la copie privée
  doit pouvoir les recevoir. Seul `template` les refuse.
- L'outil ne lit aucun XEX et ne lance aucune commande de ReXGlue. Seul `init` écrit,
  et seulement dans le dossier privé.
- Code de sortie : 0 sans constat, 1 avec constat, 2 pour un mauvais usage.

## 5. Vérifications

**Tests unitaires** (`tools/test_private_project.py`, 22 tests, dans le contrôle Nix
`private-project-selftest`) :
- le gabarit du dépôt passe, et sa version est la version épinglée ;
- un gabarit avec `function_table_base`, `setjmp_address`, `[functions]` ou une clé
  inconnue est refusé ;
- un gabarit avec un chemin absolu, `~`, une lettre de lecteur ou des `\` est refusé ;
- le `guest_path` du module se normalise comme le chemin du runtime ;
- `init` écrit une copie identique au gabarit, avec ses droits, et les dossiers de
  sortie ; les chemins se résolvent dans `game/` et `generated/` ;
- `init` n'écrit rien pour un dossier en `0755`, ni pour un dossier privé dans le dépôt,
  ni avec un mauvais gabarit, et il n'écrase pas une copie existante ;
- `check` refuse chacun des cas du tableau §4, dont un lien `game` vers l'extérieur ;
- `check` accepte une copie privée qui a reçu des adresses de phase B ;
- les codes de sortie de la ligne de commande.

**Lecture par ReXGlue** (même contrôle Nix) [V] :
- dans le bac à sable de Nix, un dossier privé synthétique est préparé par `init`. Il ne
  contient **aucun XEX** ;
- `rexglue codegen` y lit la copie. Il s'exécute avec un dossier d'application dans le
  dossier de construction et sans fichier journal ;
- il nomme le projet (`wc2010`) et son module (`1 DLL`), sans signaler de clé inconnue ;
- il résout le XEX d'entrée en `<dossier privé>/project/../game/default.xex`, puis
  s'arrête, faute de XEX, **avant de lire quoi que ce soit du jeu** ;
- il n'a écrit aucun fichier, ni dans le dossier privé ni ailleurs dans le dossier de
  construction, et la copie est inchangée. Aucun objet `xenia_memory_*` ne reste dans
  `/dev/shm`.

Le même essai, fait d'abord dans le conteneur de Claude Code, a montré le même résultat ;
`nix store verify` du SDK passait ensuite.

## 6. Destinations d'écriture de la génération de code (CP-4)

Pour une génération faite avec ce gabarit, les destinations à déclarer au contrôle
préalable sont :
- `$P/generated` : les sorties des deux modules, `codegen.d` et les repères ;
- `$P/project/wc2010_manifest.toml` : la copie, réécrite après une génération réussie ;
- le journal de ReXGlue, selon `REX_APP_ROOT` (`docs/J2_PHASE_B_CONTROLS.md`).

Un fichier d'exploits à l'ancien format sous `game/achievements/` peut aussi être réécrit
(`docs/J2_A1_SDK_INVENTORY.md` §3.1). Son existence sur ce disque est inconnue [I] ; le
contrôle après l'étape le verrait.

## 7. Limites

- Le gabarit ne prouve pas que la génération réussira : seule la phase B, avec les XEX,
  le dira [I].
- `hook_sources` et `includes` doivent se résoudre dans le dossier privé. Si J3 garde
  ses crochets dans le dépôt, cette règle sera à revoir.
- Le dossier `game/` doit contenir les deux XEX à sa racine : c'est l'arborescence du
  disque, extraite à l'étape B1. Un lien symbolique vers un autre emplacement est refusé.
